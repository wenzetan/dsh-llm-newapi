# dsh 0.2.0-rc.2 适配评估

> 历史快照：本文记录 2026-10-04 的调查结论与当时的仓库状态，不是现行兼容说明；其中的版本号、发布状态和"尚未完成"的判断都停留在该时点。现行支持边界见 [README](../README.zh-CN.md) 和 [DESIGN](../DESIGN.md)。

核对日期：2026-10-04。仓库基线：main（0.1.7 线最后一个发布提交 `0.1.7-rc.1-v0.3`）；上游固定线：npm 已发布 `@deepseek-ai/dsh@0.2.0-rc.2` 及同 family 全部 `0.2.0-rc.2` 包（npm `latest` 与 `next` 均指向它；另有 `0.2.1-alpha.1`）。

## 结论

宿主从 `0.1.7-rc.1` 升到 `0.2.0-rc.2` 后，**旧版本无法安装**：dsh 的插件安装器按 `peerDependencies` 做兼容性校验并直接拒绝。

```
dsh: installation rejected: Plugin dsh-llm-newapi@0.1.7-rc.1-v0.3 is incompatible with dsh 0.2.0-rc.2:
peerDependencies {"@deepseek-ai/dsh-llm":">=0.1.7-rc.1 <0.1.8", ...}
```

这是本轮唯一的阻塞点，也是用户报"failed to import"的根因：安装被拒后 profile 里的插件处于半安装状态，加载器拿不到可解析的 `@deepseek-ai/dsh-llm`，于是整条 `llm-newapi` 条目在导入阶段失败；同一 profile 里残留的旧 `@deepseek-ai/dsh-settings` 副本还会连带让内置 `settings` 条目报 `this.load is not a function`。

**运行时接缝没有破坏性变更**：`@deepseek-ai/dsh-llm` 0.2.0-rc.2 仍导出本插件静态引用的全部符号（`assertUsableApiKey`、`resolveRetryPolicy`、`RetryPolicySchema`、`LlmError`、`contentHasImage`、`EMPTY_RESPONSE_CODE` 等），`dsh-credentials`、`dsh-timeout`、`dsh-launch-environment` 的导出面也不变。用新依赖重跑 `npm run typecheck` 无需改动任何源码即可通过。

因此本轮按仓库既有规则**换线**：新增 `0.2.0-rc.2` 宿主线，插件版本为 **`0.2.0-rc.2-v0.1`**，peer 区间改为 `>=0.2.0-rc.2 <0.2.1`，最低版本 guard、宿主导出快照、CI 固定宿主与文档一并跟随。**合并判定：改动已完成类型、构建、组件测试、宿主兼容与真实宿主启动验证；本轮保持 RC，不执行正式版晋升。**

## 变更分析

### 依赖与版本线

- `peerDependencies`：六个接缝包从 `>=0.1.7-rc.1 <0.1.8` 改为 `>=0.2.0-rc.2 <0.2.1`。
- `devDependencies` 与 CI 固定宿主从 `0.1.7-rc.1` 升到 `0.2.0-rc.2`；`overrides` 里的 `dsh-brand` 别名同步。
- `MINIMUM_DSH_VERSION`（`src/index.ts`）从 `0.1.7-rc.1` 改为 `0.2.0-rc.2`，最低版本 guard 与 peer 元数据一致。
- 换线会触发 npm 的 ERESOLVE（旧 0.1.7 依赖仍在解析树里），按惯例删除 `package-lock.json` 与 `node_modules` 后重装。

### 运行时接缝

`@deepseek-ai/dsh-llm` 的具名导出面在 `0.2.0-rc.1` 与 `0.2.0-rc.2` 之间完全一致（两包只有 `lib/typert.host.js` 的实现不同，`lib/index.js` 的 `export {}` 逐字相同）。因此新快照 `test/fixtures/dsh-llm-0.2.0-rc.2.exports.json` 的 `surfaceSharedBy` 登记 `0.2.0-rc.1` 与 `0.2.0-rc.2`；被拒绝宿主线的对照面从 `0.1.5` 换成 `0.1.7-rc.1`。

类型、构建与全部测试在仅改 `MINIMUM_DSH_VERSION` 的情况下通过，说明 LLM adapter、模型发现、凭据、超时、launch environment、connection RPC 与客户端 slots/remote 的调用方式在 0.2.0 上仍然成立。

### 文档与 CI

- CI 固定宿主与 `boot` job 的跳过列表更新：`v0.1.5` 与 `v0.1.7` 两条旧线不再可验证（版本 guard 会拒绝），`LATEST_LINE` 改为 `v0.2.0`。
- 双语 README、`docs/development.md`、`DESIGN.md`、testbed 默认版本与说明同步换线。

## 本次实际验证

1. `npm run typecheck`：宿主与客户端类型均通过。
2. `npm run build`：`lib/index.js`、`lib/client.js` 与类型声明生成成功，产物随源码提交。
3. `npm test`：客户端组件测试 24 项、宿主兼容门禁、Cordis 组合 smoke 全部通过。
4. 打包 `npm pack` 后，在隔离 `DSH_HOME` 的全新 `web` profile 上用 dsh `0.2.0-rc.2` 安装：**不再需要 `allow-version`**，安装器接受 `0.2.0-rc.2-v0.1`。
5. `dsh web --no-open` 真实启动：**0 条 "did not activate" 告警**；认证后页面 HTTP 200，`dsh-llm-newapi/client.js` 出现在 `window.__DSH_BOOT__` 的客户端加载清单中。

## 尚未覆盖

- 未在真实浏览器里逐项操作设置页、保存凭据、触发模型发现或发起真实网关文本/工具调用；这些仍以组件测试、smoke 与 CI `boot` 的 RPC 探针为间接证据。
- 未验证 `0.2.1-alpha.1`。
- 未发布 npm：`latest` 仍指向 0.1.7 线，需推送 `v0.2.0-rc.2-v0.1` tag 后才按 `LATEST_LINE` 切到 0.2.0 线。
